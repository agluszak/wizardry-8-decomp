# `srEXT_Unzip.dll` target

This SurRender extension combines Info-ZIP UnZip 5.4 and zcrypt 2.8 with a Sir-Tech archive-stream
adapter, plug-in classes, and VC6 runtime glue. Version resources identify the upstream UnZip DLL;
compiler records and imports establish the VC6-era surrounding toolchain.

Canonical identities and evidence live in `evidence/reviewed/srext-unzip/functions.csv`;
reccmp's operational inputs live in `config/reccmp/`. Current identity totals are generated by
`just wiz8 report status`.

## Binary and SDK boundary

The DLL exports `srGetLibraryVersion` at ordinal 1 and `srInitPlugin` at ordinal 2. The factory
constructs a small wrapper and ZIP opener, then registers the `.zip` stream type through the
imported SurRender opener interface.

Decorated `SR.DLL` imports establish the stream, configuration, string-table, heap, and plug-in
contracts. The owned memory stream uses virtual inheritance: a directional input-stream subobject,
a virtual `srBinStream` base, and a local owner pointer released by the concrete destructor. Its
vtable and vbtable layouts are expressed in typed source rather than raw vptr writes.

## Recovered adapter behavior

The opener accepts paths containing `.zip` directly. Otherwise it reads `ZIP_PATH`, splits the
semicolon-separated prefixes, trims spaces, and probes each archive path. The archive parser also
handles the optional prefix before `@`, separates the `.zip` filename from its member path, and
passes both to the typed memory-extraction adapter.

The five-argument Sir-Tech wrapper constructs Info-ZIP globals, initializes the callback record,
sets redirection and case-sensitivity state, calls the upstream memory-extraction API, destroys the
globals, and frees failed output. Multiple callback matches are rejected rather than returning an
ambiguous member.

Password, print/service, replace, sound, and status callback signatures are modeled from the
canonical callback table and call sites. In particular, the password callback appends the adapter
pointer after Info-ZIP's standard arguments.

## Matching build

Build and compare with:

```sh
just build SREXT_UNZIP
just compare SREXT_UNZIP
```

The target links the pinned upstream source subset, the recovered wrapper, and the typed SurRender
slice with VC6 SP5. The narrowed Info-ZIP units retain only the memory API and WinDLL helpers present
in the original; unused stock entry points are excluded without rewriting the retained bodies.

Some comparison percentages are depressed by unnamed upstream static globals on the original side.
An unresolved reccmp placeholder is not itself a code mismatch; inspect the instruction stream
before changing source.

## Stable recovery lessons

- Vtables and callback tables exposed real function starts that auto-analysis omitted.
- Source-built FID names remained stable across several compiler recipes even when the producing
  recipe was ambiguous. Name identity and historical compiler selection are separate conclusions.
- Imported abstract stream classes are `novtable` client interfaces. Their empty imported
  destructors and the non-empty virtual base destructor must not be collapsed into one fake class.
- Reproducing the source-defined `DllMain` requires selecting the actual DLL preprocessor branch,
  while diagnostic library targets may use a different branch.
- Public upstream source should be compiled directly; only the product adapter and ABI boundary
  require independent recovery.

## Runtime replacement proof

A VC6 harness loaded the original `sr.dll`, constructed the extension through its real factory, and
exercised direct and configured archive lookup, case-sensitive and insensitive matching, prefixed
member syntax, missing/corrupt archives, multi-match rejection, repeated reads, destruction, and
clean unload. Original and rebuilt extensions agreed across those semantic scenarios.

Normal game startup does not necessarily load this extension, so a process smoke test alone is not
claimed as ZIP coverage. The explicit harness is the relevant integration boundary.

The source archive provenance and hashes remain in the configured input manifests and canonical
evidence; they are not copied into a live status section here.
